# jtcsdd

要望からウォーターフォールの設計（機能設計書）までの概念とリレーションを、どんなプロダクトにも適用できる形で管理するためのフレームワーク。仕様は **OKF（Open Knowledge Format）** の Markdown で記録し、Claude Code の**スキル**で書き、**ツール**でリレーションを機械的にチェックする。SDD（仕様駆動開発）の Spec や、日本企業的な機能設計書は、OKF から書き出す。

## 考え方

- **OKF を介する理由は、リレーションのチェックと検索を機械化するため。** 機械化するのはこの 2 つに限る。
  - フロントマター：リレーションと検索に使う情報（ID、種別、所属、参照、版、CRUD、契約の要素など）。
  - 本文：設計書が書けるだけの情報（概要、処理、エラー、ER 図、OpenAPI など）。機械チェックの対象外。
- **OKF ⇔ 設計書・Spec の変換は機械化できない**ため、スキル（Claude）が行う。ツールはチェック・検索・影響分析・導出情報の提供を担う。
- 記録は**AI が間違えないための正本**。人が読む文書はそこから書き出す。

## 概念とつながり

```
裁定 → 要望 ⇔ 要求 ⇔ 要件 ──▶ 契約 ──▶ 開発オブジェクト
（発言の記録） 〇〇したい 〇〇ができる 〇〇をする   機能契約／非機能契約

プロダクト → システム → コンポーネント → 開発オブジェクト（つくるもののツリー）
```

- **裁定**：利用者の発言と質疑を、それが何であるか（要望・調査・開発ルール・バグ報告など）を確定するまで記録したもの。
- **要望・要求・要件**：「〇〇したい」「（利用者が）〇〇ができる」「（システムが）〇〇をする」。多対多でつながる。要件は受入基準を持つ。
- **契約**：要件と開発オブジェクトの間に立つ。ER 図・OpenAPI などの単位で、コンポーネントが提供する。主従はなく、食い違いは裁定で解決する。変更の影響は契約で止め（防波堤）、契約の改版をきっかけに先へ進める。
- **版**：各概念は `revision` を持ち、参照は前提にした版 `rev` を持つ。古い版を前提にした参照は「要確認」として検出する。差分は Git、改版の理由は `log.md`。

詳しくは [docs/overview.md](docs/overview.md) と [docs/concepts/](docs/concepts/)。

## 使い方

### スキル（ワークフロー）

| スキル | 役割 | 状態 | 運用モデル（案） |
|---|---|---|---|
| okf-ruling | 発言 → 裁定 → 要望 | 作成・試験済み | Sonnet |
| okf-breakdown | 要望 → 要求 → 要件（受入基準） | 作成・試験済み | Sonnet |
| okf-structure | 要件 → 構造・契約・開発オブジェクトの骨組み | 作成・試験済み | Sonnet |
| okf-detail | 開発オブジェクトの本文と契約の定義 | 下書き | ― |
| okf-match／okf-change／okf-read／okf-write | 既存との照合／改版と影響分析／既存からの取り込み／設計書・Spec の書き出し | 未作成 | ― |

新しいシステムを作る（U1）なら okf-ruling → okf-breakdown → okf-structure → okf-detail → okf-write の順に使う。どのスキルも、人の判断が要るところ（ゲート）では提案までにとどめ、了承を得てから書き込む。ワークフローの全体は [docs/skills.md](docs/skills.md)、ユースケースは [docs/usecases.md](docs/usecases.md)。

### ツール

```bash
python tools/okf_check.py samples/tenken-note
```

| コマンド | 内容 |
|---|---|
| `okf_check.py <バンドル>` | 整合性チェック（行頭が「エラー」「警告」「突合」）。参照の存在、契約の突合、配分の合計、古い版の参照など |
| `okf_check.py <バンドル> search [--type T] [--status S] [--tag G] [--text 語]` | 検索 |
| `okf_check.py <バンドル> next-id <接頭辞>` | 採番（`REQ`、`SPC`、`OBJ-0201`、`CTR-F` など） |
| `okf_check.py <バンドル> impact <ID>` | 開発オブジェクト・契約を変えたときの直接の影響 |
| `okf_render.py <バンドル> spec\|design\|contract <ID>` | SDD Spec・機能設計書・契約書の書き出し（スキルの補助） |
| `okf_import.py <バンドル> <設計書.md>…` | 設計書から OKF への取り込み（スキルの補助） |
| `okf_io.py <バンドル> fmt` | OKF ファイルを正規形に整える |

## 進め方

- 概念とつながりは、利用者との対話で 1 つずつ決めて `docs/` に記録してきた。未決の論点は [docs/open-issues.md](docs/open-issues.md)、決めたことの履歴は [docs/log.md](docs/log.md)。
- スキルは「作る → サブエージェントで試す → 直す」を繰り返す。
  - 試験は作業用コピーで行い、利用者の役は台本で代わりに務める（ゲートの質問は記録し、了承とみなす）。
  - 同じ条件で Opus と Sonnet を比べ、運用するモデルを決める（Haiku は候補から外した）。
  - 試験の題材は、references の例と重ならないものにする。
- 変更はまとめてコミットする。
