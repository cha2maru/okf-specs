# OBJ-020102：点検写真登録API

> 例：ファイルを受け取る API の方式の選択理由と、サイズ・形式チェックの順序を書く（題材：点検ノートの点検写真登録API）

<!-- 写真の形式（JPEG、長辺 2048px 以下）とオブジェクトキーは CTR-F-006（キー規約）に、
     リクエスト・応答の形式は CTR-F-001 に書く。ここではチェックの順序と方式の判断を書く。 -->

## 概要

点検結果に写真を 1 枚追加する。同じ n で再送された場合は上書きする。呼び出し元は端末の同期処理で、圏外からの回復時にまとめて送る。

## 方式

アップロードの方式は 3 案を比べ、**A：API がファイルを直接受け取る** を採った。

| 案 | 流れ | 長所 | 短所 |
|---|---|---|---|
| A：API が直接受け取る（採用） | 端末 → PUT（本文が画像）→ API がバケットに保存 | 1 回の呼び出しで終わり、同期処理の再試行が単純。形式チェックを保存前にできる | API のコンテナが画像を中継するため、帯域とメモリを使う |
| B：署名付き URL | 端末 → API で URL を発行 → 端末がバケットへ直接 PUT → 完了通知 API | 大きいファイルや大量の送信で API に負荷がかからない | 3 回の呼び出しのどこで切れても回復できる状態管理が要る。形式チェックは保存後（バケットのイベントで別処理） |
| C：multipart/form-data | 端末 → POST（複数ファイル）→ API | 1 回で複数枚送れる | 途中で切れると全部送り直し。圏外が多い現場に向かない |

- A を採った理由：写真は端末側で長辺 2048px に縮小してから送るため 1 枚 1〜2MB で、件数も 1 日 1 拠点 数百枚程度のため。
- 1 枚が 10MB を超える用途（動画など）を足すときは B に切り替える。そのときは本 API とは別の開発オブジェクトにする。

## 認証・認可

共通方針どおり（点検者のアクセストークン）。加えて、点検結果の拠点が点検者の担当拠点であること（他拠点の点検結果に写真を足せない）。

## 入力の業務制約

チェックは、本文を読む前にできるものから順に行う（大きい不正ファイルを最後まで受け取らないため）。

1. `n` が 1〜10 の整数であること（1 点検あたり 10 枚まで）。
2. `Content-Type` が `image/jpeg` であること。
3. `Content-Length` があり、5MB 以下であること。ない場合（チャンク転送）は受け取らない。
4. 点検結果テーブル（OBJ-020401）に `id` が存在し、担当拠点であること。
5. 本文を読み、先頭が JPEG のマジックナンバー（`FF D8 FF`）であること。`Content-Type` だけを信用しない。
6. 画像のヘッダから幅・高さを読み、長辺が CTR-F-006 の上限以下であること（画像全体の展開はしない）。

ロードバランサー（OBJ-040101）の本文サイズ上限は 6MB に設定する（API の上限より少し大きくし、413 を API 側で返せるようにする）。

## 処理

1. 入力の業務制約を上の順に確かめる。
2. EXIF から位置情報（GPS）を取り除く。撮影日時と向き（Orientation）は残す。
3. CTR-F-006 のキーで写真バケットに保存する。同じキーがあれば上書きする。
4. 成功を返す。

点検結果テーブルは更新しない（写真の枚数は、バケットのキーの一覧から数える）。

## 出力

成功時の応答本文はなし。新規と上書きの区別、ステータスは CTR-F-001 による。

## エラー

| 条件 | ステータス | メッセージ ID | 文言 |
|---|---|---|---|
| `n` が範囲外 | 400 | E-0211 | 写真は 10 枚まで登録できます |
| JPEG でない（Content-Type・マジックナンバー） | 415 | E-0212 | 写真の形式が不正です |
| 5MB を超える・Content-Length がない | 413 | E-0213 | 写真のサイズが大きすぎます |
| 長辺が上限を超える | 400 | E-0214 | 写真のサイズが大きすぎます |
| 点検結果が存在しない | 404 | E-0215 | 点検結果が見つかりません |
| 担当外の拠点 | 403 | 共通 | 共通方針どおり |
| 本文の受信が 60 秒で終わらない | 408 | ― | （端末の同期処理が再送する） |
| バケットへの保存失敗 | 503 | 共通 | 共通方針どおり |

## 排他・トランザクション・冪等性

- 同じ `id`・`n` の PUT は何度送っても結果が同じ（上書き）。端末の再送で枚数が増えることはない。
- 同じ `id`・`n` への同時の PUT は、後に保存した方が残る（排他はしない。同じ端末から同じ写真が送られる前提）。
- DB への書き込みがないため、DB とバケットの整合は考えなくてよい。点検結果の削除は今のところない。

## ログ

共通方針どおり。画像の中身は出さない。`id`・`n`・バイト数・幅・高さ・処理時間を INFO で出す。
