# OBJ-210101：注文登録API

> 例：登録 API の冪等キー・排他・イベント発行との整合を、契約（OpenAPI）と重ねずに書く（題材：EC の注文登録API）

<!-- リクエスト・レスポンスの項目と型、Idempotency-Key ヘッダが必須であることは CTR-F-201（注文API、提供：CMP-2101）に書く。
     発行する注文確定イベントの項目は CTR-F-204（受け手：在庫管理の CMP-1103）に書く。 -->

## 概要

会員のカートの内容から注文を 1 件登録し、注文確定イベントを発行する。在庫の引当はイベントを受けた在庫管理システムが非同期に行うため、この API では在庫を確保しない。

## 認証・認可

- 共通方針どおり（会員のアクセストークン）。
- 注文の会員 ID はトークンから取る。リクエストに会員 ID は持たせない（他人名義の注文を防ぐ）。

## 入力の業務制約

- 明細は 1〜50 行。同じ商品 ID の明細を 2 行以上持たない。
- 商品が商品テーブル（OBJ-210405）に存在し、販売状態が「販売中」であること。
- 数量は 1〜99。商品ごとの購入上限（商品テーブルの値）を超えないこと。
- 単価はリクエストの値を使わず、商品テーブルの現在の価格で計算し直す。リクエストの `expectedTotal`（画面に表示した合計）と一致しなければ 409（価格変更）を返す。
- 配送先は会員の登録済み住所の ID だけ受け付ける（住所の文字列は受け付けない）。

## 処理

1. 冪等キーテーブル（OBJ-210403）を（会員 ID, Idempotency-Key）で検索する（冪等性の節）。
2. 入力の業務制約を確かめる。
3. 1 つのトランザクションで次を行う。
   1. 注文（OBJ-210401）を状態＝受付で登録する。注文番号は採番テーブルではなく、DB のシーケンスから作る。
   2. 注文明細（OBJ-210402）を登録する。
   3. アウトボックス（OBJ-210404）に注文確定イベントを 1 行登録する。
   4. 冪等キーテーブルの行を「完了」にし、応答本文を保存する。
4. コミットしたら 201 と注文番号を返す。
5. イベントの送信はアウトボックス中継処理（OBJ-210301）が行う。この API はブローカーに直接送らない。

## 出力

201：登録した注文の注文番号・合計金額・状態。冪等キーの再送で既に完了していた場合も、保存した応答本文をそのまま 201 で返す（初回と同じ応答にするため）。

## エラー

| 条件 | ステータス | メッセージ ID | 文言 |
|---|---|---|---|
| 必須項目なし・形式不正 | 400 | E-2101 | 入力内容に誤りがあります |
| 販売中でない商品を含む | 422 | E-2102 | 販売を終了した商品が含まれています |
| 購入上限を超える | 422 | E-2103 | {商品名}は{上限}個までご購入いただけます |
| 合計金額が変わった | 409 | E-2104 | 価格が変更されました。内容をご確認ください |
| 同じ冪等キーで別の内容 | 422 | E-2105 | （画面には出さない。クライアントの不具合） |
| 同じ冪等キーの要求を処理中 | 409 | E-2106 | （画面には出さない。Retry-After: 1 を付ける） |
| DB 接続不可・タイムアウト | 503 | 共通 | 共通方針どおり |

## 排他・トランザクション・冪等性

- 冪等キーテーブルの行は（会員 ID, キー, 要求本文のハッシュ, 状態, 応答本文, 有効期限＝24 時間）。
  - 行がない：状態＝処理中で登録してから処理する（一意制約で同時の 2 要求の片方だけが通る）。
  - 完了でハッシュが一致：保存した応答を返す。ハッシュが違えば 422。
  - 処理中：409（同時の再送）。処理中のまま 60 秒を過ぎた行は失敗とみなし、上書きして処理し直す。
- 注文・明細・アウトボックスを同じトランザクションで書くことで、「注文はあるのにイベントがない」「イベントだけ出た」を起こさない。イベントは少なくとも 1 回届く（重複は受け手が排除する。CTR-F-204）。
- 在庫を確保しないため、商品行のロックは取らない。価格の読み取りとコミットの間に価格が変わっても、読んだ時点の価格で確定する。

## ログ

共通方針どおり。配送先住所・電話番号は出さない。注文番号・会員 ID・冪等キー・合計金額を INFO で出す。
