# CTR-N-001：予約画面の応答性能

## 目標

| 項目 | 内容 |
|---|---|
| 数値 | 2.0 秒以内を p95 で満たす。p99 は 4.0 秒以内（参考値、未達でも不合格にしない） |
| 計測区間の起点 | 予約確認画面で「予約する」ボタンを押したとき（クリックイベント） |
| 計測区間の終点 | 予約完了画面の予約番号が表示されたとき（描画完了） |
| 対象の操作 | 予約の登録だけ。空き枠の検索は CTR-N-002 で別に定める |
| 由来 | SPC-012（予約は待たされずに完了する）、RUL-005（競合店の調査から 2 秒） |

## 計測条件

| 項目 | 条件 |
|---|---|
| 同時利用者数 | 300 人（ピーク：金曜 12 時の実績 180 人の 1.6 倍） |
| 予約の登録件数 | 毎秒 20 件 |
| データ量 | 店舗 500、予約 1,000 万件（3 年分）、空き枠 200 万件 |
| 端末 | 中位のスマートフォン相当（CPU 4 倍遅延のエミュレーション） |
| 回線 | 4G 相当（往復 50 ミリ秒、下り 10 Mbps）。端末⇔ロードバランサー間の通信時間は 0.1 秒とみなす |
| キャッシュ | 画面の静的ファイルは取得済み（初回表示は対象外） |

## 配分の考え方

合成ルールは直列和。区間を順に並べ、足して目標に収める。

| 区間 | 配分先 | 配分値 | 合成 |
|---|---|---|---|
| ボタン押下 → 要求の送信、応答の受信 → 描画 | CMP-0101 予約画面（全体） | 0.3 秒 | 足す |
| 端末 ⇔ ロードバランサーの通信 | なし（計測条件で固定） | 0.1 秒 | 足す |
| ロードバランサー・WAF の通過（往復） | CMP-0201 ネットワーク（全体） | 0.1 秒 | 足す |
| 予約登録 API の処理 | OBJ-010201 予約登録API（一部） | 1.2 秒 | 足す |
| └ 予約・空き枠テーブルの更新（排他を含む） | OBJ-010501・OBJ-010502（一部） | 0.4 秒 | API の 1.2 秒に**内包**（足さない） |
| 余裕 | ― | 0.3 秒 | 足す |
| 合計 | | 2.0 秒 | |

- 実行環境（CMP-0204）への配分は時間ではなく**条件**（スケールアウトが追いつくこと）。合計には足さない。
- テーブルを objects で指すのは、同じデータストアの他のテーブル（会員・店舗）は対象外のため。API も同じコンポーネントの他の API（一覧・取消）は対象外のため objects で指す。
- 画面とネットワークはコンポーネントのどの部分を通っても同じ値でよいため component で指す。
- 未配分の区間：なし（端末⇔ロードバランサーは計測条件で固定し、余裕とは分ける）。

## 測定・検証方法

| 対象 | 手段 | タイミング | 環境 |
|---|---|---|---|
| 目標（全体） | 負荷試験ツールで計測条件の負荷をかけつつ、ブラウザ自動操作で 200 回測る | リリース前・四半期ごと | 性能検証環境（本番と同じ台数・データ量） |
| 目標（本番） | 画面の計測ビーコン（起点・終点の時刻）を集計し、日次で p95 を出す | 常時 | 本番 |
| CMP-0201 の配分 | ロードバランサーの処理時間の指標 | 常時 | 本番（OBJ-020101 の監視） |
| OBJ-010201 の配分 | API のアクセスログの処理時間 | 常時 | 本番・性能検証 |
| OBJ-010501・010502 の配分 | DB のスロークエリログ（0.2 秒超を記録）と実行計画 | リリース前 | 性能検証 |

## 未達時の扱い

- リリース前の試験で未達：配分ごとの実測を比べ、超えた配分先が改善する。超えた配分先がなく余裕を食いつぶした場合は、配分の見直しを裁定で決める。
- 本番で日次の p95 が 3 日続けて未達：性能改善の要件を起こし、次のリリースで対応する。
- 配分値を変えるときはこの契約を改版し、配分先の開発オブジェクトを要確認にする。
