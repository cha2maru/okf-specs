# 契約

## 定義

[要件](/concepts/specification.md)と[開発オブジェクト](/concepts/product-tree.md)の間に置く取り決め。
システムやコンポーネントをつなぐ設計（DB なら ER 図、API なら Swagger 等）を契約の中に持つ。

## 目的

契約という単位で、DB の更新や API の変更が**どの設計に波及するか**をリレーションで表す。

## 種別

要件の分類に合わせて、契約を 2 種類に分ける。

| 種別 | 対応する要件 | つながり方 | 内容 |
|---|---|---|---|
| 機能契約 | 機能要件 | コンポーネントが**提供**し、開発オブジェクトが**利用**する（範囲を記載可） | ER 図、Swagger 等 |
| 非機能契約 | 非機能要件 | 全体の目標をコンポーネントへ**配分**する（配分ごとに値を持つ） | 品質特性、目標値、配分値 |

以下「単位と提供者」〜「例：API ゲートウェイ」は機能契約についての記述。

## 単位と提供者

- 契約の単位は ER 図・Swagger などとし、粒度は**コンポーネント**にそろう。
- 契約は**コンポーネントが提供**する。

| 契約の中身 | 提供するコンポーネント | 中に含まれる開発オブジェクト |
|---|---|---|
| ER 図 | 会員DB | 会員テーブル、注文テーブル … |
| Swagger | 公開API | POST /members、GET /members/{id} … |

## 契約への参照

要件（`contracts`）と開発オブジェクト（`uses`）からの機能契約への参照は、同じ形で書く。

- 契約**全体**を指すときは、**コンポーネントの参照**（`component`）として書く。値は契約の提供コンポーネントと一致させる。
- 契約の**一部**を指すときは、**開発オブジェクトの参照の配列**（`objects`）として書く。いずれも提供コンポーネント配下の開発オブジェクトとする。
- `component` と `objects` はどちらか一方だけを書く。
- 非機能契約への参照は契約だけを書く（配分は契約側に持つ）。
- データ（テーブル・ファイル）を指す場合は `crud` を付けられる（試行中）。

```yaml
# 要件
contracts:
  - { contract: /contracts/CTR-F-007.md, component: /structure/CMP-0203.md }   # 契約全体
  - { contract: /contracts/CTR-F-003.md, objects: [/structure/OBJ-020402.md] } # 一部
  - { contract: /contracts/CTR-N-002.md }                                      # 非機能
# 開発オブジェクト
uses:
  - { contract: /contracts/CTR-F-003.md, objects: [/structure/OBJ-020401.md], crud: CR }
```

参照先が明示されるため、影響分析は「変更された開発オブジェクトを参照先に含む要件・開発オブジェクト」に絞り込める。

```
コンポーネント：会員DB ──提供──→ 契約：会員DB（ER図）
                                     ▲
                       ┌──利用───────┴──利用──┐
            開発オブジェクト：会員登録API    開発オブジェクト：月次集計
                                              （範囲：[会員テーブル]）
```

## 厚さ

つながりがあれば、そこには必ず契約が存在する。ただし内容の厚さは許容幅を持つ。

| つながり | 契約 | 内容 |
|---|---|---|
| システムをまたぐ | 存在する | 厚い（ER 図、Swagger 等） |
| 同一システム内 | 暗黙的に存在する | 薄くてよい（つながりの事実だけでもよい） |

同一システム内の DB を後から別システムへ切り出す場合も、契約の内容を厚くするだけで構造は変わらない。

## 例：API ゲートウェイ

API ゲートウェイの Swagger と、バックエンド API のマッピングは契約として表す。

```
システム：APIゲートウェイ
  └ コンポーネント：公開API（Swagger）──提供──→ 契約：公開API
                                                    ▲ 利用
システム：Webアプリ                                  │
  └ コンポーネント：会員管理                         │
      ├ 開発オブジェクト：会員登録API ───────────────┤
      └ 開発オブジェクト：会員参照API ───────────────┘
```

## 契約の中身の置き場所

- フロントマターには契約に含まれる**要素の一覧**（`elements`：エンティティ名、オペレーション、メッセージ名など）を置く。突合はこの一覧と開発オブジェクトの間で機械的に行う。
- ER 図・OpenAPI などの本体は、OKF の本文に書く。大きい場合は別ファイルに置き `resource` で参照してもよい。
- 本文の ER 図・OpenAPI と `elements` の食い違いは、AI レビュー（本文が解析できる形式ならツール）で確かめる。

```yaml
type: 機能契約
id: CTR-F-003
title: 点検DB
provider: /structure/CMP-0204.md
format: ER図
resource: design/er/tenken-db.md
elements: [拠点, 設備, 点検結果]
```

## 主従関係とレビュー

- 契約には**主従関係がない**。提供側・利用側のどちらかが正ということはない。
- 契約内容（ER 図・OpenAPI 等）と開発オブジェクトの間に差異があれば、それは当事者間の**衝突**であり、どちらを直すかは**裁定**で決める（[裁定](/concepts/ruling.md)）。
- レビューは**契約単位**で行う。契約書（`tools/okf_render.py contract`）には、契約内容・提供コンポーネントの開発オブジェクト・突合結果・利用者・参照する要件・レビュー欄を載せる。
- 突合は ER 図（エンティティ ↔ テーブル）と OpenAPI（オペレーション ↔ API）で自動化し、それ以外は目視とする。
- レビュー欄に確認者・確認日時を記入して取り込むと、OKF の `verified`（OKF v0.2）に反映される。

## 影響の伝播（契約は防波堤）

契約は、内側の変更を外へ漏らさない防波堤として扱う。

1. 開発オブジェクトが変更されると、そのオブジェクトを参照する要件と、利用側の開発オブジェクトが「要確認」になる。影響は**利用側の開発オブジェクトで止める**。
2. 利用側で対応した結果、その利用側が提供する契約が変わるかを、人または AI が判断する。
3. 変わる場合だけ**契約を改版**し、その改版をきっかけに、さらに先へ影響分析を進める。

```
拠点テーブル変更
  → 異常通知処理（要確認）  ■ ここで止める
      判断：異常イベント契約（CTR-F-007）は変わるか？
        No  → 終了
        Yes → CTR-F-007 を改版 → POST /inspections（要確認）→ …
```

## IaC が提供する機能契約

DB の接続先やバケットなど、IaC が提供するものは **IaC における機能**とみなし、機能契約として表す。

- 例：CTR-F-008 DB接続（提供：データ基盤コンポーネント）、CTR-F-009 写真バケット（提供：ストレージ基盤コンポーネント）
- アプリ側の開発オブジェクトは、この契約を `component` 参照で利用する。アプリは接続の取り決めだけに依存し、クラスタ構成には依存しない。
- これにより、同じ「点検 DB」が**論理**（ER 図・テーブル：アプリのシステム）と**物理**（DB クラスタ：クラウド基盤のシステム）に分かれても、その間を契約でつなげる。

## 論理と物理（realizes）

物理側の契約（IaC の接続情報など）は `realizes` で論理側の契約（ER 図・キー規約）を指す。逆向きは書かない（ツールで導出する）。

```yaml
# CTR-F-008 DB接続
realizes: /contracts/CTR-F-003.md
```

## 突合（elements と開発オブジェクト）

| 形式 | 開発オブジェクト側 |
|---|---|
| OpenAPI | 提供コンポーネント配下の API の `operation` |
| ER 図・端末内スキーマ・キー規約 | 提供コンポーネント配下のテーブル・ファイルの `entities` |
| メッセージ定義・接続情報・外部 API | 機械的な突合はしない |

食い違いはチェッカーが「突合」として報告し、契約に主従はないため裁定で解決する。

## 非機能契約

非機能要件そのものを契約として記載し、目標を個々のコンポーネントへ配分する。
暗号化・可用性など物理側で実現するものは、IaC のコンポーネントへ配分する。

```
契約：応答性能（非機能）
  目標：画面操作の応答 3 秒以内
  配分 ─┬→ 会員DB         ：クエリ 500ms 以内
        ├→ 認証（機能群）  ：処理 1 秒以内
        └→ 公開API         ：ゲートウェイ遅延 200ms 以内

契約：可用性（非機能）
  目標：SLA 99.9%
  配分 ─┬→ クラウド基盤（IaC）：マルチ AZ 構成
        └→ 会員DB            ：自動フェイルオーバー
```

- 配分先も契約への参照と同じく、コンポーネント全体なら `component`、一部なら `objects`（開発オブジェクトの配列）で書き分ける。

```yaml
allocations:
  - { component: /structure/CMP-0402.md, value: 保存時暗号化（KMS） }
  - { objects: [/structure/OBJ-020101.md], value: 異常イベント発行まで 10 秒以内 }
```

- 数値で表せる目標には `unit` と `target_amount` を付け、各配分に数値の `amount` と `role` を付ける。
  - `加算`：目標に足し込む。加算の合計が `target_amount` を超えないことをチェックする。
  - `内包`：`within` の配分の内側（足さない）。`within` の `amount` を超えないことをチェックする。
  - `条件`：時間を持たない前提（`amount` なし）。

```yaml
unit: 秒
target_amount: 3.0
allocations:
  - { component: /structure/CMP-0202.md, value: API 応答 1.5 秒以内, amount: 1.5, role: 加算 }
  - { objects: [/structure/OBJ-020401.md], value: 集計クエリ 0.5 秒以内, amount: 0.5, role: 内包, within: /structure/CMP-0202.md }
```

- 監査ログのような横断的な要件も非機能契約（セキュリティ）として扱う。
- 「コンポーネント単位の品質目標」は、配分をコンポーネント側から見たビューとして得られる。
- 品質特性の分類には IPA 非機能要求グレードや ISO/IEC 25010 を用いることができる（未決）。

## リレーション

- [要件](/concepts/specification.md) → 契約（機能要件 → 機能契約、非機能要件 → 非機能契約）
- コンポーネント →（提供）→ 機能契約
- 開発オブジェクト →（利用・範囲）→ 機能契約
- 非機能契約 →（配分・配分値）→ コンポーネント または 開発オブジェクト
