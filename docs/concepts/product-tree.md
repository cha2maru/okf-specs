# 成果物ツリー

## 定義

実際につくるものを、日本企業における機能設計書の構造を想定したツリーで表す。
ツリーは**所属**だけを表し、ツリーをまたぐつながりは[契約](/concepts/contract.md)で表す。

## 階層

| 階層 | 名称 | 指すもの | 種別の例 |
|---|---|---|---|
| 1 | プロダクト | プロダクト全体 | ― |
| 2 | システム | デプロイ・インストールの単位。IaC で表せるクラウド基盤を指すこともある | アプリ、基盤 |
| 3 | コンポーネント | 概念的、もしくはディレクトリで分けられる単位 | 機能群、データストア、ファイル群、API 定義 |
| 4 | 開発オブジェクト | 単体で設計する単位（画面 1 つ、API 1 本など） | 画面、API、バッチ、帳票、テーブル、ファイル |

- DB・ファイル・API 設計も、システムの下にこのツリーで入れる。
- IaC で管理するクラウド基盤もシステムとし、リソースのまとまり（ネットワーク、データ基盤、ストレージ基盤、実行環境など）をコンポーネント、個々のリソース定義を開発オブジェクト（種別：IaCリソース）とする。
- コンポーネント・開発オブジェクトは「機能」という語を避け、中身の違いは**種別**で表す。種別ごとの書き方は `templates/okf/`。
- テーブル・ファイルは `entities` で、提供する契約のどの要素を載せるかを示す（命名規則には頼らない）。
- 画面は `roles`（使うアクター）と `transitions`（遷移先の画面）を持つ。
- IaC リソースは `depends_on`（前提とする他のリソース）を、実行環境は `hosts`（動かすアプリの開発オブジェクト）を持つ。

## 名称の決定理由

- **開発オブジェクト**：日本企業の「開発オブジェクト一覧」と同じ粒度。「要素」は画面要素（ボタン等）のような細かい単位を連想させるため採用しない。オブジェクト指向の「オブジェクト」と区別するため「開発オブジェクト」と呼ぶ。
- **コンポーネント**：DB を「サブシステム」と呼ぶのは不自然なため、中立的な名称とした。

## 例

```
プロダクト：会員サービス
├─ システム：Webアプリ
│   ├─ コンポーネント：会員管理（機能群）
│   │   ├─ 開発オブジェクト：会員登録画面（画面）
│   │   └─ 開発オブジェクト：会員登録API（API）
│   ├─ コンポーネント：会員DB（データストア）
│   │   └─ 開発オブジェクト：会員テーブル（テーブル）
│   └─ コンポーネント：外部連携ファイル（ファイル群）
│       └─ 開発オブジェクト：会員CSV（ファイル）
├─ システム：APIゲートウェイ（基盤）
│   └─ コンポーネント：公開API（API定義）
└─ システム：クラウド基盤（基盤）
```

## リレーション

- コンポーネント →（提供）→ [契約](/concepts/contract.md)
- 開発オブジェクト →（利用・範囲）→ 契約
- 開発オブジェクト → 設計（未整理）
