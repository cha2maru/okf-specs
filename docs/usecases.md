# ユースケース

スキル化の前に、スキル・ワークフローが対応すべきユースケースを洗い出したもの。

- **⚠ 流れが変わる可能性**：基本の流れ（裁定 → 要望 → 要求 → 要件 → 契約 → 開発オブジェクト）から外れる、または逆向きになるもの。扱いは**今後の課題**とする（[未決事項](/open-issues.md) #41〜#45）。

## 作る

| # | ユースケース | 起点 | 主な流れ | 人の判断が要るところ |
|---|---|---|---|---|
| U1 | 要望 1 つからシステムを作る | 発言 | 裁定 → 要望 → 要求 → 要件（受入基準） → 構造（システム・コンポーネント） → 契約 → 開発オブジェクト → 設計書・Spec → 実装 | 構造の切り方、契約の境界 |
| U2 | 既存のプロダクトに要望を足す | 発言 | 裁定 → 要望 → 既存の要求・要件との照合（新規か、既存に紐づけるか。多対多） → 不足分だけ要件・契約・開発オブジェクトを追加 → 既存の契約を改版するなら影響分析 → 差分の設計書・Spec | 既存の要件で満たせるか、契約を変えるか |
| U3 ⚠ | 既存システムを OKF に取り込む（リバース） | コード、DB、OpenAPI、IaC、既存の設計書 | 構造と契約を起こす → 開発オブジェクトの本文 → 要件を逆算 → 要望・裁定は「出典不明（既存）」として起こす | 逆算した要件が正しいか、どこまで遡るか |

## 変える

| # | ユースケース | 起点 | 主な流れ | ポイント |
|---|---|---|---|---|
| U4 | 仕様変更（既存の要件・契約を直す） | 発言、設計中の気づき | 対象を改版 → `rev` が古い参照を要確認として洗い出す → 利用側を確認して `rev` を上げる | 「契約で止め、改版で先へ」の運用 |
| U5 ⚠ | バグ報告 | 発言 | 裁定で「バグ報告」に振り分け → 原因の層を判定（要件の誤り／契約の誤り／実装の誤り） → 要件なら U4、契約の食い違いなら U9、実装だけなら受入基準を追加して実装へ | 開発オブジェクトを直接指すことがある |
| U6 | 非機能の見直し（SLA 変更、性能問題） | 発言、監視 | 非機能契約の目標・配分を改版 → 合計のチェック → 配分先の開発オブジェクトを要確認に | `amount`／`role` のチェック |
| U7 | 基盤の移行・技術の刷新 | 方針の決定 | 物理側（IaC、接続情報の契約）だけを改版 → `realizes` で論理の契約は変えずに済むことを確認 → アプリ側の影響を限定 | 論理と物理の分離 |
| U8 ⚠ | 機能の廃止・縮小 | 発言 | 要望を却下、要求・要件を廃止（deprecated） → 下流で使われなくなる契約・開発オブジェクトを検出 → 削除か残すかを判断 | 廃止の伝播はまだチェックがない |

## 確かめる

| # | ユースケース | 内容 |
|---|---|---|
| U9 | 契約単位のレビューと衝突の裁定 | 突合の差異を裁定にかけ、どちらを改版するか決める（#29 裁定の記録形式が必要） |
| U10 | 調べる・問い合わせる（読むだけ） | 「この要件はどこで実装されているか」「このテーブルを変えたら何に響くか」「未確定の要件は」など。検索と影響分析 |
| U11 ⚠ | 実装とのずれの検出 | SDD で実装したあと、コード（OpenAPI、DDL、IaC）と OKF の食い違いを見つける。U3 の差分版 |
| U12 | 確定・ベースライン | レビュー済み（`verified`）にして stable に上げる。リリース時点で Git のタグを付ける |

## 文書にする

| # | ユースケース | 内容 |
|---|---|---|
| U13 | 設計書・SDD の Spec を書く | OKF から Claude が機能設計書・契約書・Spec を書く |

## 範囲外の候補（今後の課題）

| # | ユースケース | 理由 |
|---|---|---|
| U15 ⚠ | 複数プロダクトでの共通基盤の共有 | プロダクトをまたぐ契約。今のモデルはプロダクトが 1 つの前提 |
| U16 ⚠ | テストとの対応（V 字の右側） | 受入基準 ID とテストの対応（#33 と関連） |
| ― | 裁定の行き先「調査」「開発ルール」 | 以前から今後の課題としている |

## 流れが変わる可能性のあるもの（今後の課題）

| # | 何が変わるか |
|---|---|
| U3 | 下から上への逆算になる。要望・裁定の出典が分からない（「既存」として起こす扱いが必要）（#42） |
| U5 | バグ報告は要件・契約を経ずに**開発オブジェクトを直接指す**ことがある。「要件は必ず契約を経由する」の外側の経路になる（#41） |
| U8 | 廃止が上流から下流へ伝播する。使われなくなったものの検出規則がない（#43） |
| U11 | 実装（コード）が起点になる。OKF とコードのどちらを正とするか（#44） |
| U15・U16 | プロダクトの外、V 字の右側にモデルを広げる必要がある（#45） |

## 共通する部品

ユースケースを分解すると繰り返し出てくる部品。スキルはこの部品の単位で作り、ユースケースは部品を組み合わせたワークフローにする方向。

| 部品 | 使うユースケース |
|---|---|
| 裁定（発言を受けて振り分ける） | U1, U2, U4, U5, U8, U9 |
| 既存との照合（新しいものを既存の要求・要件・契約に対応づける） | U2, U3, U5 |
| ブレークダウン（要望 → 要求 → 要件） | U1, U2, U3（逆向き） |
| 構造・契約の設計 | U1, U2, U3, U7 |
| 改版と影響分析（`rev` の更新まで） | U2, U4, U6, U7, U8 |
| 突合と衝突の裁定 | U3, U9, U11 |
| 読み取り（コード・既存の設計書 → OKF） | U3, U11, U14 |
| 書き出し（OKF → 設計書・Spec） | U1, U2, U13 |
| 検索・問い合わせ | U10、ほか全部の下支え |
