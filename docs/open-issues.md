解決・前進した事項：

- #2・#3 → 差分は Git、改版理由は log.md。各概念に `revision`、参照に前提とした版 `rev` を持たせ、古い版が前提の参照を要確認として検出する（概要「版と履歴」）。
- #15 → 契約を防波堤とし、影響は利用側の開発オブジェクトで止める。契約が変わるかは人／AI が判断し、改版をきっかけに先へ進める（改版の記録は #2・#3 で決定）。
- #27 → 非機能の配分先も `component`／`objects` で書き分ける形にして解決。
- #23 → 画面は契約とみなさない。要求・要件の補足情報（ユースケース）で画面を参照するだけとし、Spec・機能設計書にはその参照から画面を載せる形で解決。
- #8 → クラウド基盤を IaC コンポーネント・開発オブジェクトまで分解し、可用性・暗号化を IaC コンポーネントへ配分して解決。DB 接続先などは IaC が提供する機能契約とした。

- #16 → 契約参照を「コンポーネントの参照／開発オブジェクトの参照」で書く形にして解決。
- #17 → SPC-006 に拠点テーブルへの参照を追加して Spec に DB が現れるようになった。漏れの機械検出は未解決。
- #18 → `crud` を試行。「拠点テーブルを登録・更新する開発オブジェクトがない」を検出でき、Spec の Open Questions と機能設計書の確認事項に出力された。

既存論点のサンプルでの実例：

- #7 主語ルールの例外 → REQ-006「点検データは端末を紛失しても第三者に読まれない」（主語がデータ）
- #8 配分先がシステム全体 → CTR-N-003 可用性は本来クラウド基盤システム全体に配分したいが、実行基盤コンポーネントに配分した

その他の確認結果：

- 非機能要件は利用者から自発的に出ず、裁定での質問によって引き出された（裁定に質疑を含める設計が有効）。
- 受入基準は要求から導出し、要件の属性（本文の「受入基準」節）として持たせられた。
