# メタモデル概要

## 目的

- 単なる要望を、ウォーターフォールにおける設計書まできちんと整理する。
- 要求から詳細設計までのリレーションと各属性を整理し、「どこで何を決定するか」と「変更の影響」を管理できるようにする。
- 特定のプロダクトに依存せず、どんなプロダクトにも適用できる枠組みとする。

## 記録の位置づけ

- OKF で記録するのは、**AI が間違えないための正本**である。人が読みやすいことより、参照が明示的で機械的に検証できることを優先する。
- SDD の Spec や日本企業的な機能設計書は、OKF から**生成する出力物**とし、手で編集しない。修正は OKF 側で行う。
  - 試作：`tools/okf_render.py`（生成）、`tools/okf_check.py`（整合性チェック・影響分析）
  - 出力例：`samples/out/tenken-note/`
- SDD の Spec には、要望・要求・要件のすべて（ID・本文・つながり）と、関わる Structure の対象すべて（プロダクト → システム → コンポーネント → 開発オブジェクトのツリーと役割）を書く。

## 全体の流れ

```
【要求側の流れ】
裁定 → 要望 ⇔ 要求 ⇔ 要件            （要望〜要件は多対多）
                      │
                      ▼ できる限り具体的な契約を指す
                    契約（ER図・Swagger 等）
                      │  提供：コンポーネント
                      │  範囲：開発オブジェクトの配列
                      ▼
                 開発オブジェクト → 設計

【構造側のツリー】
プロダクト → システム → コンポーネント → 開発オブジェクト
```

要求側の流れと構造側のツリーは、**契約**と**開発オブジェクト**で出会う。

## 概念一覧

| 概念 | 位置づけ | 詳細 |
|---|---|---|
| 裁定 | 発言・質問・回答のやりとりを、それが何かを確定するまで記録したもの | [裁定](/concepts/ruling.md) |
| 要望 | 「〇〇したい」 | [要望](/concepts/wish.md) |
| 要求 | 「（利用者が）〇〇ができる」 | [要求](/concepts/requirement.md) |
| 要件 | 「（システムが）〇〇をする」 | [要件](/concepts/specification.md) |
| 契約 | 要件と開発オブジェクトの間に置く取り決め | [契約](/concepts/contract.md) |
| プロダクト／システム／コンポーネント／開発オブジェクト | 実際につくるもののツリー | [成果物ツリー](/concepts/product-tree.md) |

## リレーションの原則

1. 要望 ⇔ 要求 ⇔ 要件 は**多対多**。新しい要求が既存の要件に対応することもある。
2. 要件は**必ず契約を経由**して開発オブジェクトに至る。要件から開発オブジェクトへ直接紐づけない。
3. ツリーは**所属**を表し、システムやコンポーネントをまたぐつながりは**契約**で表す。
4. 変更の影響は「要件 → 契約 → 開発オブジェクト」の経路でたどる。

## 版と履歴

- 各概念はフロントマターに整数の `revision` を持つ。意味のある変更をしたら上げる（何を「意味のある変更」とするかは #4 で未決）。
- 参照する側は、前提にした上流の版を `rev` に記録する。対象は `from`（要望 → 要求 → 要件）、`contracts`、`uses`。

```yaml
from:
  - { ref: /requirements/REQ-004.md, rev: 1 }
contracts:
  - { contract: /contracts/CTR-F-007.md, component: /structure/CMP-0203.md, rev: 1 }
```

- 上流の `revision` が `rev` より新しい参照は「要確認」とする。利用側が確認を終えたら `rev` を上げる。これが [契約](/concepts/contract.md) の「改版をきっかけに先へ進める」の仕組みになる。
- 内容の差分は **Git** に任せ、「どの概念をなぜ改版したか」は OKF の `log.md` に書く。旧版の本文は OKF の中に持たない（AI が旧版を現行と取り違えないため）。

```
## 2026-10-03
- CTR-F-007 を r2 に改版（siteName を追加）。契機：OBJ-020402 拠点テーブルの変更
```

## 実現したいこと

- 要件を指定すると、紐づく要求・要望（・裁定）とその**内容の変化の履歴**を機械的にたどって確認できる。
- 契約単位で、DB の更新や API の変更がどの設計に波及するかをリレーションで表す。

未決の論点は [未決事項](/open-issues.md) を参照。
