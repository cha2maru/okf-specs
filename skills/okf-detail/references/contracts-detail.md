# 契約の定義の詳しさ

契約の本文には、当事者が合意するのに足りる定義を書く。契約に主従はないので、提供側の都合だけで決めない。

| 形式 | 書くこと |
|---|---|
| OpenAPI | `info`、全オペレーション（`elements` と一致）、全パラメータ（パスパラメータを含む）、全レスポンス（成功応答の本文、エラー）、エラー本文の共通形式、`securitySchemes`、制約（`minItems`・`maxLength` など）、互換性の方針 |
| ER 図 | 全エンティティ（`elements` と一致）と関連、エンティティごとの「1 行が表すもの」、主な属性（型・必須・キー）、整合のルール、データ量・保存期間、他システムからの参照方法 |
| メッセージ定義 | 配送基盤・宛先、配送保証、順序、重複時の扱い、項目（`eventId`・`occurredAt`・`schemaVersion` を含む）と必須、例、失敗時の扱い（DLQ）、互換性 |
| 接続情報定義 | 提供する値（`elements` と一致）、渡し方、シークレットの構造とローテーション、TLS・権限、障害時に利用側がすべきこと |
| キー規約 | キー形式と変数の範囲、ファイル形式・上限、メタデータ、読み取り側の取り決め、上書き・削除 |
| 外部API仕様 | 利用範囲（API ごとの項目の対応表）、認証、冪等性、エラーコードの意味、上限・SLA。先方の仕様を写さない |

## 食い違いを作らない

- 開発オブジェクトの本文にあるエラー（400・404 など）は、契約の OpenAPI のレスポンスにも定義する。処理で返すと書いた値（例：201 で inspectionId を返す）は、契約の成功応答の本文に定義する。
- テーブルの項目定義と ER 図の属性を一致させる。
- 処理で使う項目（例：イベントの `siteId`）が、契約のどこから来るかをたどれるようにする。たどれなければ【要確認】。
