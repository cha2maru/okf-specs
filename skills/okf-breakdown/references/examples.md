# 良い例・悪い例

## 要求

| 悪い例 | 何が悪いか | 良い例 |
|---|---|---|
| スマホで点検できるようにする | 主語がない。手段（スマホ）だけ | 点検者はスマホで点検項目の結果と写真を記録できる |
| 管理者がダッシュボード画面で拠点一覧 API を使って進捗を見る | 画面・API（手段）を書いている | 管理者は拠点ごとの当月の点検進捗を確認できる |
| 点検者は圏外でも記録でき、管理者は異常をすぐ知ることができる | actor も能力も 2 つ | 2 つの要求に分ける |
| 基幹システムと連携できる | 利用者の能力ではなく制約 | 裁定の行き先を「調査」にする |

## 要件

| 悪い例 | 何が悪いか | 良い例 |
|---|---|---|
| 異常をすぐに通知する | 「すぐに」が曖昧。機能と非機能が混ざっている | 機能：クラウドは異常ありの点検結果を受信したら拠点の管理者へメールで通知する／非機能：受信から 5 分以内に送信する |
| ダッシュボードは高速に表示する | 測れない | ダッシュボードは拠点進捗を 3 秒以内（p95）に表示する |
| 点検結果を保存し、写真も保存し、通知もする | 1 つの要件に 3 つの振る舞い | 保存と通知を分ける |

## 受入基準

| 悪い例 | 何が悪いか | 良い例 |
|---|---|---|
| 正しく保存されること | 観察できない | 前提：圏外／操作：3 件記録してアプリを再起動／結果：3 件が「未送信」として残っている |
| 管理者にメールが届くこと | 外部サービスに依存し、自分たちで保証できない | 受信時刻から送信 API の受付時刻までが 5 分以内 |
| 速いこと | 計測条件がない | 拠点 100・設備 10,000・当月点検結果 10,000 件で、画面を開いてから描画まで p95 が 3 秒以内 |

## 実例（点検ノート）

- 要望 [WSH-004]「異常が見つかったらすぐ知りたい」
- → 要求 REQ-004「管理者は異常のある点検結果を発生後すぐに知ることができる」（actor: 管理者、from: WSH-004, WSH-003）
- → 要件 SPC-006（機能）「クラウドは異常ありの点検結果を受信したら拠点の管理者へメールで通知する」
- → 要件 SPC-008（非機能）「クラウドは異常通知を点検結果の受信から 5 分以内に送信する」

ファイルの実物はフレームワークの `samples/tenken-note/` にある。
