# 書き方の規則

## 3 つの層の文の形

| 層 | 文の形 | 主語 | 例 |
|---|---|---|---|
| 要望 | 〇〇したい | 発言者 | 電波が届かない場所でも点検したい |
| 要求 | 〇〇ができる | 利用者・業務（`actor`） | 点検者は圏外でも点検を記録でき、通信回復後に事務所と共有できる |
| 要件 | 〇〇をする | システム | モバイルアプリは圏外時も点検結果を端末内に保持する |

- 語尾だけで区別せず、**主語**で区別する。要求の主語は `actor`（プロダクトの `actors` にある名前）、要件の主語はシステム名（「モバイルアプリは」「クラウドは」など）。
- 主語が利用者・業務でない要求（例：「点検データは端末を紛失しても第三者に読まれない」）は例外として認める。`actor` を付けず、本文に「actor を付けない理由」を書く。

## 要求

- 1 つの要求には 1 つの能力だけを書く。「〜でき、〜できる」と 2 つ並ぶ場合は、分けるか、一続きの能力として書けるかを考える。
- 手段（画面・技術）を書かない。「ダッシュボードで」「外出先で」程度の利用場面は書いてよいが、画面の項目や API は書かない。発言で手段（「メールで」など）が指定されていたら、要件の側に書く。
- ユースケース（`usecase`）は補足。手順の中で画面を参照するだけで、画面を決めるものではない。

## 要件

- 1 つの要件は、1 つの検証できる振る舞い。「〜し、〜する」は分けられないか考える。
- 機能要件（`category: 機能`）と非機能要件（`category: 非機能`）を混ぜない。
  - 機能：何をするか（保存する、通知する、表示する）。
  - 非機能：どれだけよく（何秒以内、稼働率、暗号化）。数値か、確かめられる条件で書く。
- 曖昧な語（「すぐに」「適切に」「十分な」「など」）を残さない。数値・条件に置き換えるか、【要確認】にする。
- 曖昧な動詞（「管理する」「対応する」「扱う」）を使わない。登録する・変更する・表示する・通知する、のように検証できる動詞にする。
- データの持ち方（ID の組、上書きなど）や実装の方式は書かない。それは構造・開発オブジェクトの側で決める。

## 受入基準

- ID は `AC-<要件番号>-<連番>`（例：SPC-012 → AC-012-1）。フロントマターの `acceptance` に ID、本文に文章。
- 機能要件：**前提／操作／結果**。結果は観察できることだけを書く（「正しく処理される」は不可）。
- 非機能要件：**計測条件と合格基準**（例：拠点 100・点検結果 10,000 件で、p95 が 3 秒以内）。
- 外部サービスが絡む場合は、自分たちで責任を持てる範囲までにする（例：メールの到着ではなく、送信 API の受付まで）。
- 否定の結果（「異常がなければ通知しない」）も、必要なら 1 つの基準として書く。
- 1 つの要件に、正常系と、意味のある異常系・境界（該当なし、権限外など）を別の基準として付ける。前提だけが違って結果が同じ基準は 1 つにまとめる。
- 操作は利用者（または外部）の行為として書く。「クラウドが受け取る」のようにシステムの内部動作を操作にしない。
