# okf-breakdown：要望 → 要求 → 要件

要望（〇〇したい）から、要求（利用者が〇〇ができる）と要件（システムが〇〇をする）を起こし、OKF バンドルに書く。

## 前提

- **フレームワークのファイル**：このスキルのディレクトリから 2 つ上（プラグインのルート）に `templates/okf/` と `tools/` がある。見つからなければリポジトリ内を探し、それでもなければ利用者に聞く。
- **OKF バンドル**：`rulings/`・`wishes/`・`requirements/`・`specifications/` を持つディレクトリ。分からなければ利用者に聞く。
- **ツール**：`python <フレームワーク>/tools/okf_check.py <バンドル> [コマンド]`
  - 引数なし：整合性チェック（各行の先頭が「エラー」「警告」「突合」で区分される）／ `search --type 要求 --text 語`：検索（タイトル・本文・ユースケースの手順が対象）／ `next-id REQ`：採番（ファイルを書く前は同じ値を返すので、複数起こすときは返った値から自分で連番を振る）
- フロントマターはリレーションのチェックと検索のためだけに使い、本文には設計書が書けるだけの情報を書く。
- **発言にない事実を書かない。** 仮定したことは、本文に必ず `【要確認：仮定＝…】` と書く。印のない仮定を残さない。

## 手順

### 1. 対象を確かめる

- 最初にチェッカーを実行し、出力を控えておく（手順 6 で差分だけを見るため）。
- 対象の要望（`wishes/WSH-xxx.md`）と、その出典の裁定（`from`）を読む。要望が `wishes/index.md` に載っていなければ、報告で利用者に伝える（一覧への追加は okf-ruling の担当）。プロダクトの `actors`（`structure/PRD-xxx.md`）も読む。
- `disposition` が `採用` でない要望は、進めてよいか利用者に確かめる（`未整理` なら採否も一緒に確かめる）。

### 2. 既存の要求・要件と照合する

- `search --type 要求` と `search --type 要件` で、同じこと・近いことを言っているものを探す。キーワードを 2〜3 個変えて検索する。
- **文字列が一致しなくても**、既存の要求の**ユースケース**（`usecase`）と、それが参照する**画面**を読み、新しい要望が同じ画面・同じ手順に関わらないかを確かめる（例：「担当分だけ見たい」は、既存の「設備を一覧から選ぶ」の一覧を絞り込む関係）。
- 関係が見つかったら、`references/patterns.md` の「3. 既存の要件で満たせる」「9. 既存の前提が変わる」「10. 既存の要件に振る舞いを足す」を読み、扱いを決める。利用者への提示は手順 3 にまとめる。
- 関係が見つからなかった場合も、検索したキーワードと結果を、手順 3 の提示に一言含める。

### 3. 要求を起こす　【ゲート：要求の確定】

- テンプレート `templates/okf/03-requirement.md` に従う。`status: draft`。
- 書く前に `references/wording.md`（「3 つの層の文の形」「要求」）と `references/examples.md`（要求の良い例・悪い例）を読む。分け方は `references/patterns.md` の 1・2・6・7・8 を見る。
- ユースケースで参照したい画面がまだない場合は、その手順の `screen` を省く（画面は okf-structure で起こす）。
- 利用者への提示は **1 回にまとめる**：
  1. 要求の案（ID、文、actor、由来する要望、ユースケース）と、分けた・まとめた理由
  2. 手順 2 の照合の結果
  3. **非機能の質問**：`references/patterns.md` の「5. 非機能を引き出す質問」から、この要望に関係する観点だけを 2〜3 個選ぶ
  4. 要求の範囲を決めるのに必要な質問
- **了承を得るまで次に進まない。** 答えが出なかった質問は、仮定を置いて `【要確認：仮定＝…】` と書き、手順 4 に進んでよいか確かめる。

### 4. 要件を起こす　【ゲート：要件の確定】

- テンプレート `templates/okf/04-specification.md` に従う。`status: draft`。
- 書く前に `references/wording.md`（「要件」「受入基準」）と `references/examples.md`（要件・受入基準の例）を読む。
- 1 つの要求に対して、機能要件と非機能要件を分けて起こす。主語はシステム。動詞は検証できるもの（「管理する」「対応する」のような曖昧な動詞は使わない）。
- **非機能要件**：手順 3 で利用者から数値や条件が得られたものだけ起こす。**仮定の数値では起こさない。** 得られなかった場合は、要求の本文の「非機能」節に「なし（理由）」または「REQ-xxx に準ずる」と書き、未確認の観点は【要確認】にする。
- **受入基準**：
  - フロントマターの `acceptance` に ID を並べる（`- { id: AC-<要件番号>-<連番> }`）。本文に文章を書く。
  - 機能要件は「前提／操作／結果」。正常系と、意味のある異常系・境界（該当なし、権限外など）を別の基準にする。同じことを言う基準を重ねない。
  - 非機能要件は「計測条件と合格基準」。
- **`contracts` はフィールドごと省く**（テンプレートでは必須だが、okf-structure で書く。チェッカーは draft の間は警告にとどめる）。
- データの関係（どのテーブルに何を持つか）や実装の方式は書かない。決まっていない関係は【要確認】にして okf-structure に回す。
- 発言から論理的に導いた振る舞い（例：管理者だけが振り替えられる → 管理者以外は拒否する）は、案として書き、利用者に確かめる。**確かめられていない導出には【要確認：仮定＝…】を付ける。**
- 発言で指定された手段（「メールで」など）は要件に書き、要求には書かない。
- 要件の案を利用者に見せ、**了承を得てから**書き込む。

### 5. 書き込みと記録

- 要求・要件のファイルを書く。`requirements/index.md` に 1 行、`specifications/index.md` は `category` に合った節（機能要件／非機能要件）に 1 行ずつ足す。
- 手順 1 で採否を確かめた場合は、要望の `disposition` を更新する。
- バンドルの `log.md` に、その日の見出し（なければ作る）の下へ「WSH-xxx から REQ-xxx、SPC-xxx〜xxx を起こした」と 1 行書く。

### 6. チェックと報告

- チェッカーを実行し、手順 1 の出力との**差分**を見る。新しく出た「エラー」の行は直す。
- 新しく出た「要件が契約に紐づいていない」の警告は想定どおり（okf-structure で解消する）。新しく出た「突合」は内容を利用者に伝える。
- 利用者への報告に含めるもの：
  - 起こした要求・要件の一覧
  - **残っている【要確認】の一覧**（ファイルと内容）
  - 次は okf-structure（構造・契約の設計）であること

## やらないこと

- 契約・コンポーネント・開発オブジェクトを起こすこと（okf-structure の担当）。
- 利用者の了承なしに、既存の要求・要件の文を書き換えること（意味が変わる変更は改版。okf-change の担当）。
- 発言にない事実を、【要確認】の印なしに書くこと。
