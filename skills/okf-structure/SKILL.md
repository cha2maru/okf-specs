# okf-structure：要件 → 構造・契約・開発オブジェクトの骨組み

要件（`status: draft`、`contracts` なし）を実現するための構造と契約を決め、OKF バンドルに書く。

## 前提

- **フレームワークのファイル**：このスキルのディレクトリから 2 つ上（プラグインのルート）に `templates/okf/`（テンプレートと `examples/`）と `tools/` がある。見つからなければリポジトリ内を探し、それでもなければ利用者に聞く。
- **OKF バンドル**：`specifications/`・`structure/`・`contracts/` を持つディレクトリ。分からなければ利用者に聞く。
- **ツール**：`python <フレームワーク>/tools/okf_check.py <バンドル> [コマンド]`
  - 引数なし：整合性チェック（行頭が「エラー」「警告」「突合」）／ `search`：検索 ／ `next-id`：採番（`SYS`、`CMP-02`、`OBJ-0201`、`CTR-F`、`CTR-N`。書く前は同じ値を返すので、複数起こすときは自分で連番を振る）／ `impact <ID>`：影響分析
- **契約が要件と開発オブジェクトの間に立つ。** 要件は必ず契約を経由して開発オブジェクトに至る。契約には主従がない。
- **既存のものを優先する。** 既存のシステム・コンポーネント・契約で実現できるなら、新しく起こさない。
- 発言・要件にない事実を書かない。仮定には `【要確認：仮定＝…】` を付ける。

## 手順

### 1. 対象を確かめる

- 最初にチェッカーを実行し、出力を控えておく（手順 7 で差分だけを見るため）。
- 対象の要件（契約のない要件）と、その要求・要望を読む。
- 既存の構造をつかむ：`structure/index.md`、システム・コンポーネントの一覧（`search --type システム`、`search --type コンポーネント`）、契約の一覧（`contracts/index.md`）。システムの「共通方針」も読む（なければ、手順 2 の提示で「共通方針なし（okf-detail で決める）」と伝える）。

### 2. 構造を決める　【ゲート：構造の確定】

- 書く前に `references/decomposition.md` を読む。
- 要件ごとに、どのシステム・コンポーネントが担うかを決める。既存で担えるものは既存を使い、足りないものだけ新しく起こす案を作る。
- 構造の判断を左右する要件側の【要確認】（例：担当者は 1 人か複数か）は、このゲートで質問してよい。答えは要件の文には書かず、報告に「okf-breakdown で反映すること」として挙げる。
- 利用者が「未定」と答えたもの（例：認証の仕組み）は起こさず、関係するファイルに【要確認】を付けて報告に列挙する。
- 利用者に提示する：要件 → システム・コンポーネントの対応表、新しく起こすシステム・コンポーネント（ID、名前、種別、理由）、既存を使う理由、見つけた不足（`references/decomposition.md` の「よくある不足」）、既存の契約を改版する見込み（あれば予告）。
- **了承を得るまで書き込まない。**

### 3. 契約を決める　【ゲート：契約の境界の確定】

- 書く前に `references/contracts.md` を読む。形式ごとの書き方は `templates/okf/30〜36` と `templates/okf/examples/contract/` を見る。
- 機能要件ごとに、指す機能契約と参照先（契約全体＝`component`、一部＝`objects`）を決める。非機能要件ごとに、非機能契約と配分（`component` か `objects`、数値の目標なら `unit`・`target_amount`・`amount`・`role`）を決める。
- **既存の契約に要素を足す・変える必要がある場合**は、その契約の改版になる。改版する契約、足す要素、影響を受ける利用者（`impact <契約ID>`）を一覧にする。
- 利用者に提示する：
  - 要件 → 契約の対応表
  - 新しい契約（ID、形式、提供コンポーネント、`elements`、厚さ）
  - **改版する既存の契約**（表の列：契約、改版の内容、追加だけか変更か、影響を受ける要件、要確認になる開発オブジェクト。`impact` は改版の前に実行する）
  - 非機能の配分（合計が目標以下であること。利用者が配分の値を決められなければ、仮の値に【要確認：仮定＝…】を付ける）
- **了承を得るまで書き込まない。**

### 4. 開発オブジェクトの骨組みを起こす

- 書く前に `references/objects.md` を読む。種別ごとのテンプレートは `templates/okf/20〜27`。
- 契約の `elements` に対応する開発オブジェクト（API、テーブル、ファイル）を起こす（`operation`／`entities` を契約と一致させる）。
- 契約を利用する開発オブジェクト（画面、イベント処理、バッチなど）を起こし、`uses` を書く（契約、参照先、データなら `crud`、`rev`）。
- 画面は `roles`（プロダクトの actors）と、分かる範囲の `transitions`。IaC は `depends_on`、実行環境は `hosts`。
- **サーバー側で動く開発オブジェクト**（API・イベント処理・バッチ・オンライン処理）を起こしたら、実行環境の IaC リソースの `hosts` に足し、DB・ファイルを使うなら、それを実現する接続情報の契約（`realizes` でたどる）も `uses` に足す。
- 本文は「概要」だけ書く（他の節は okf-detail が書く）。名前だけ出てくるもの（マスタ、キュー、鍵など）も開発オブジェクトとして起こす。

### 5. 書き込む

- 新しいシステム・コンポーネント・契約・開発オブジェクトを、テンプレートに従って書く。`status: draft`。
- 契約の本文：「当事者」と、定義の骨組み（ER 図ならエンティティと主な関連、OpenAPI ならオペレーションと主な入出力）を書く。詳細は okf-detail で厚くする。
- **順序**：既存の契約の改版を先に行い、そのあと要件の `contracts` を書く（`rev` に改版後の版を書くため）。
- 既存の契約を改版する場合：`revision` を 1 上げ、`elements` と本文を直し（「当事者」の節がなければ足す）、バンドルの `log.md` に「CTR-x を rN に改版（追加だけ／変更：理由）」と書く。改版した契約を前提にしていた既存の参照は「要確認」としてチェッカーに出る（解消は okf-change の担当。この手順では一覧にして報告する）。
- 要件に `contracts` を書く（`rev` は契約の現在の `revision`）。
- 要求のユースケースで、新しく起こした画面を参照できるようになったものは `screen` を足す。
- 既存の開発オブジェクトの `uses` に、改版した契約への参照を足すときは、**既存の行は触らず**、現在の `rev` を書いた別の行で足す。
- 既存の開発オブジェクト・要求に参照（`uses`、`hosts`、`screen`）を足しても、その `revision` は上げない（意味の変わる変更は okf-change の担当）。
- `structure/index.md`（ツリー）と `contracts/index.md` を更新する。`log.md` に、起こしたものを 1 行で書く。

### 6. 要件を確定するか確かめる

- 契約が紐づいた要件・要求を `stable` にするかを利用者に聞く。【要確認】が残っているものは draft のままにする。

### 7. チェックと報告

- チェッカーを実行し、手順 1 の出力との**差分**を見る。
  - 新しく出た「エラー」は直す。
  - 新しく出た「どの実行環境にも載っていない」「接続情報の契約を使っていない」の警告は直す。
  - 新しく出た「突合」（契約の `elements` と開発オブジェクトの食い違い）は直す。直せない（どちらを正とするか決められない）ものは裁定が要るものとして報告する。
  - 配分の合計の超過は直す。
  - 改版による「要確認（古い版を前提にしている）」は一覧にして報告する。
  - このスキルで解消した既存の行（例：起こしたテーブルで消えた突合）も報告する。
- 利用者への報告に含めるもの：起こしたもの・改版したものの一覧、残っている【要確認】、要確認の参照、次は okf-detail（開発オブジェクトの本文と契約の詳細）であること。

## やらないこと

- 要求・要件の文を変えること（変える必要があれば利用者に伝え、okf-breakdown か改版で扱う）。
- 開発オブジェクトの本文（処理・エラー・画面項目など）を書くこと（okf-detail の担当）。
- 改版で生じた要確認の参照の `rev` を上げること（影響の確認は okf-change の担当）。
