# 構造の切り方

## 階層

| 階層 | 何で分けるか | 種別（kind） |
|---|---|---|
| システム | デプロイ・インストールの単位。IaC で管理するクラウド基盤もシステム。自分たちで作らない外部サービスもシステム | アプリ／基盤／外部 |
| コンポーネント | 概念やディレクトリで分けられるまとまり。契約を提供する単位（1 コンポーネントが提供する機能契約は原則 1 つ） | 機能群／データストア／ファイル群／API定義／IaC |
| 開発オブジェクト | 単体で設計する単位（画面 1 つ、API 1 本、テーブル 1 つ、IaC リソース 1 つ） | 画面／API／イベント処理／バッチ／バックグラウンド処理／オンライン処理／テーブル／ファイル／IaCリソース |

## 判断の目安

- **既存で担えるか**を最初に考える。既存のコンポーネントの責務（本文の「責務」）に収まるなら、そこに開発オブジェクトを足す。
- **DB は独立したコンポーネント**（データストア）にする。複数の機能群が同じテーブルを使うのが普通だから。
- **API 定義**（OpenAPI 1 つ）を 1 コンポーネントにする。利用者（呼ぶ側）が違う API は、コンポーネント（＝契約）を分ける（例：スマホ向けの点検API と、ダッシュボード向けの管理API）。
- **論理と物理を分ける**：アプリ側のデータストア（ER 図）と、それを載せる IaC 側のリソース（DB クラスタ）は別のシステムに置き、IaC 側が提供する接続情報の契約でつなぐ（`realizes`）。
- **外部サービス**は `kind: 外部` のシステムとし、利用する API をコンポーネント（API定義）にする。
- **画面の置き場所**：画面は使うアクター・端末ごとのシステム（モバイルアプリ、管理ダッシュボード）の機能群に置く。
- **横断的なもの**（認証、監査ログ、共通マスタ）を、個々の機能群に埋め込まない。共有されるなら独立したコンポーネントにする。
- 新しいシステムを起こすのは、デプロイの単位が増えるときだけ。機能が増えるだけならコンポーネントか開発オブジェクトで足りる。

## よくある不足

構造を決めるときに、要件には書かれていないが必要になるもの。見つけたら提示に含める。

- **マスタ**：要件が「設備ごと」「担当者ごと」と言っているのに、設備・担当者を持つテーブルがない。
- **取得の手段**：画面に一覧を出すのに、それを返す API がない（端末内データだけでは足りない場合）。
- **登録・更新の手段**：テーブルを読む機能はあるのに、書く機能がない（チェッカーの「登録・更新する開発オブジェクトがない」）。
- **認証・認可**：アクターごとに見せる範囲が違うのに、認可の仕組みがない。
