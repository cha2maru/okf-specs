# 契約の決め方

## 機能契約の形式

| 形式 | 使う場面 | 提供コンポーネント | `elements` | 突合の相手 |
|---|---|---|---|---|
| OpenAPI | API を公開する | API定義 | オペレーション（`POST /path`） | 開発オブジェクトの `operation` |
| ER図 | 複数の機能が DB を共有する | データストア | エンティティ名 | テーブルの `entities` |
| 端末内スキーマ | 端末内の DB | データストア（アプリ側） | エンティティ名 | テーブルの `entities` |
| キー規約 | ファイルを置き場に置く | ファイル群 | ファイル名 | ファイルの `entities` |
| メッセージ定義 | イベントを非同期に渡す | 受け付ける側の機能群 | メッセージ名 | （機械的な突合なし） |
| 接続情報定義 | IaC が接続先を渡す | IaC | 渡す値の名前 | （機械的な突合なし）。論理の契約を `realizes` |
| 外部API仕様 | 外部サービスを使う | 外部システムの API定義 | 利用する API | （機械的な突合なし） |

- **厚さ**：システムをまたぐなら `厚い`、同一システム内なら `薄い`。同一システム内でも複数の機能群が使う DB は厚くしてよい。
- `{}` を含むオペレーションは `"…"` で囲む。

## 要件から契約への参照

- 機能要件 → 機能契約、非機能要件 → 非機能契約。
- **できる限り具体的に**指す：契約の一部だけに関わるなら `objects`（開発オブジェクトの配列）、契約全体なら `component`（提供コンポーネント）。
- 要件が必要とするデータ（例：通知先のメールアドレスを持つテーブル）も、その契約を参照に含める。漏れると、影響分析と Spec の材料から抜ける。

## 非機能契約

- 1 つの非機能要件に 1 つの非機能契約が基本。同じ品質特性でも目標が違えば分ける。
- 配分は `component`（全体）か `objects`（一部）。暗号化・可用性など物理側で実現するものは IaC のコンポーネントへ配分する。
- 数値の目標には `unit`・`target_amount` を付け、各配分に `amount` と `role` を付ける。
  - `加算`：目標に足し込む（合計が `target_amount` を超えない）。
  - `内包`：`within` の配分の内側（足さない）。
  - `条件`：時間を持たない前提（外部サービスの SLA など）。
- 配分のない区間（ネットワークなど）を残さない。残すなら本文に理由を書く。
- 計測の起点・終点になる処理（例：保存の API の完了）は配分ではなく、本文の「目標」に計測区間として書く。
- 配分の値の根拠になる設計上の仮定（例：同期の取得間隔 5 分）は、配分先の開発オブジェクトの本文にも【要確認】付きで書く。

## 既存の契約を改版するとき

- `elements` が変わるときだけでなく、**本文の定義が変わるとき**（既存のエンティティに項目を足す、など）も改版になる。

- 契約に主従はない。改版は、提供側・利用側のどちらから見ても変更になる。
- 改版する契約ごとに `impact <契約ID>` で利用者を出し、提示に含める。
- 要素を**足すだけ**（既存のオペレーション・エンティティを変えない）なら、利用側への影響は小さい。既存の要素を**変える・消す**なら、利用側の確認が必要。どちらかを `log.md` の改版理由に書く。

## 契約は防波堤

- 開発オブジェクトの中身の変更は、その契約が変わらない限り、利用側に波及しない。
- 構造を決めるときは、変わりやすいもの（内部の処理）を契約の内側に、変わりにくいもの（受け渡すデータの形）を契約に置く。
